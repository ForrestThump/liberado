## Cross-session insights distilled

**Parallel research agents beat serial reads for broad doc audits.** Splitting a ~34-file docs tree
into three independent agents (specs+architecture, roadmap, contributing/getting-started/reference/ideas)
made the audit tractable in one round-trip rather than serial reads that would fill the context window
with low-signal text. The key constraint is splitting along genuinely independent axes, not just
arbitrary file groups — overlapping scope would produce duplicated findings and miss nothing.

**Claim-vs-code spot-checking is the highest-value audit step.** Grepping for the struct/function/route
a doc claims exists (not just reading the doc) caught two undocumented API routes (`GET /api/catalog`,
`PATCH /api/conversations/{id}`) that a text-only read missed, and confirmed the merger of
`config-plan.md` was safe because every one of its "next steps" was already implemented. The
discipline: before declaring a doc stale, confirm the code that would make it current actually exists.

**A cheap link-checker catches bugs no human read-through catches.** Walking `docs/`, extracting
markdown links with a simple regex, and verifying each target path exists found 22 broken links —
including some predating this session entirely. Most were a consistent root-relative-vs-file-relative
path bug. The lesson: add a link-check step to the doc-audit standard operating procedure.

**"Record findings before fixing" is load-bearing for audits.** The hygiene and hardening audit docs
(`hygiene-audit-2026-07-02.md`, `hardening-audit-2026-07-02.md`) each got their own commit before the
corresponding fix commit. This pattern lets a differently-scoped session (or a different agent) resume
the backlog without re-deriving it, and the findings doc survives even if the fix is later reconsidered
— something a chat transcript that compacts away does not provide.

**The MCP child-process sandboxing gap is a system-level constraint, not a code bug.** Item 1 of the
hardening audit is documented here because it shapes what's achievable via code patches: a local
process that can write to the vault filesystem is indistinguishable from a human editor at the
attribution layer. Integrity signing (item 2) catches *field tampering* but cannot catch *who* set
`status: approved` because that field must remain editable. Any session that revisits this should start
from the OS-level isolation / out-of-band approval channel framing, not from "what code can we add to
`handle_proposal_change`."
